# cert-helper — план дальнейшей доработки (ROADMAP)

Этот документ собирает **все** идентифицированные направления доработки
демона на текущий момент: то, что уже обсуждалось в ходе разработки, но
не было реализовано, плюс функциональность, заимствованная из анализа
похожих инструментов (Squid `ssl_crt_validator`/AIA-докачка, nginx OCSP
stapling, HAProxy, service mesh-практики resiliency). Пункты 1–5 из
анализа Squid (HTTP cache hints, двухуровневый кэш, сетевая политика,
эластичный пул, per-type наблюдаемость) уже реализованы — см. README.md,
раздел «Доработки по итогам анализа Squid». Всё ниже, кроме пунктов,
явно помеченных **[СДЕЛАНО]** (см. README.md, раздел «Доработки по
ROADMAP.md»), — **не реализовано**, сгруппировано по темам, с пометкой
приоритета и объёма работ.

Легенда приоритета: **P0** — дефект безопасности/корректности, стоит
делать в первую очередь; **P1** — заметно улучшает надёжность/эксплуатацию;
**P2** — полезно, но не срочно; **P3** — nice-to-have/долгосрочное.

---

## 1. Безопасность и корректность (P0–P3)

Не закрытые ранее замечания — сформулированы до анализа Squid, остаются
актуальными:

1. **[СДЕЛАНО] [P0] TTL AIA-сертификата, ограниченный его собственным
   `notAfter`.** Было: TTL кэша для докачанного промежуточного
   сертификата — `min(aia_ttl_seconds, HTTP cache hints)`, без учёта
   срока действия самого сертификата (если сертификат истекает через 2
   дня, а `aia_ttl_seconds` — неделя, демон 5 дней отдавал бы уже
   просроченный сертификат). Реализовано: `notAfter` докачанного
   сертификата дополнительно клампит TTL сверху —
   `ttl = min(ttl, notAfter - now)`; если `notAfter` уже в прошлом —
   сертификат вообще не кладётся в кэш. См.
   `request_router.hpp::clamp_ttl_to_cert_not_after()` /
   `handle_intermediate_cert_impl`, README.md раздел «Доработки по
   ROADMAP.md», тесты
   `test_intermediate_cert_ttl_clamped_to_cert_not_after` и
   `test_intermediate_cert_already_expired_not_cached` в
   `tests/test_client_server_roundtrip.cpp`.

2. **[СДЕЛАНО] [P0] Верхняя граница TTL для OCSP/CRL.** Было: TTL
   берётся из `nextUpdate` ответа без ограничения сверху —
   недобросовестный или скомпрометированный responder может указать
   `nextUpdate` через год, и демон будет год отдавать устаревший статус
   отзыва (cache poisoning с очень долгим действием). Реализовано:
   `max_ocsp_ttl_seconds`/`max_crl_ttl_seconds` (по умолчанию 24ч/7
   дней, флаги `--max-ocsp-ttl-seconds`/`--max-crl-ttl-seconds`),
   клампят `ttl = min(ttl, max_ttl)` независимо от заявленного
   `nextUpdate`. См. `request_router.hpp::clamp_ocsp_ttl()`/
   `clamp_crl_ttl()`, README.md раздел «Доработки по ROADMAP.md», тесты
   `test_ocsp_ttl_clamped_to_max_ocsp_ttl` и
   `test_crl_ttl_clamped_to_max_crl_ttl` в
   `tests/test_client_server_roundtrip.cpp`.

3. **[СДЕЛАНО] [P1] Ключ OCSP-кэша через `CertID`, а не сырые байты
   запроса.** Было: `der_fingerprint(request_der)` ломается, если
   tls-mitm добавит nonce в OCSP-запрос (RFC 8954, рекомендуемая защита
   от replay) — тогда каждый запрос по одному сертификату даёт разный
   DER, и кэш никогда не срабатывает. Реализовано: разбирается
   `OCSP_ONEREQ`/`OCSP_CERTID` из `request_der` (hash issuer name +
   issuer key + serialNumber), ключуется по нему, игнорируя
   nonce-расширение; при неразборе — откат на прежний фингерпринт всего
   DER. См. `request_router.hpp::ocsp_request_cache_fingerprint()`,
   README.md раздел «Доработки по ROADMAP.md», тест
   `test_ocsp_cache_key_ignores_nonce_but_distinguishes_certid` в
   `tests/test_client_server_roundtrip.cpp`.

4. **[СДЕЛАНО] [P1] Лимиты размера ответа по типу запроса, а не одна
   константа.** Было: `SimpleHttpFetcher::recv_all` ограничивал любой
   ответ 32 МиБ. OCSP весит единицы КБ, AIA-сертификат — пара КБ, CRL
   может быть до нескольких МБ. Разрешать 32 МБ на "OCSP-ответ" — лишняя
   поверхность для исчерпания памяти/диска. Реализовано:
   `max_response_bytes` — обязательный параметр `IHttpFetcher::fetch()`,
   `RequestRouter::Config::max_ocsp_response_bytes`/
   `max_aia_response_bytes` (по умолчанию 256 КиБ) и
   `max_crl_response_bytes` (по умолчанию 16 МиБ), флаги
   `--max-ocsp-response-bytes`/`--max-aia-response-bytes`/
   `--max-crl-response-bytes`. Заодно обнаружен и исправлен
   use-after-free в `dbus_client.hpp::call_and_parse_fetch()`
   (см. README.md). См. README.md раздел «Доработки по ROADMAP.md»,
   тесты `test_response_exceeding_max_bytes_is_rejected`/
   `test_response_within_max_bytes_is_accepted` в
   `tests/test_http_cache_hints.cpp` и
   `test_response_size_limits_differ_per_request_type` в
   `tests/test_client_server_roundtrip.cpp`.

5. **[СДЕЛАНО] [P1] Singleflight-дедупликация параллельных одинаковых
   запросов.** Было: если много TLS handshake одновременно упираются в
   один и тот же URL при промахе кэша — каждый запрос независимо
   инициировал свой HTTP-запрос. Реализовано: паттерн "in-flight
   requests" — `RequestRouter::singleflight_execute()` оборачивает
   `handle_ocsp`/`handle_crl`/`handle_intermediate_cert`; если запрос к
   ключу уже выполняется, остальные ждут его результата на
   `condition_variable`, а не дублируют сетевой поход. Особенно важно при
   "громком стаде" (thundering herd) на старте, когда кэш пуст. См.
   README.md раздел «Доработки по ROADMAP.md», тест
   `test_singleflight_deduplicates_concurrent_identical_requests` в
   `tests/test_client_server_roundtrip.cpp`.

6. **[СДЕЛАНО] [P2] PKCS#7 "degenerate" контейнер как формат ответа
   `caIssuers`.** Было: поддерживался только голый DER X.509;
   PKCS#7-контейнер (`application/pkcs7-mime`, который используют
   некоторые CA для caIssuers) трактовался как InvalidResponse.
   Реализовано: `extract_single_der_certificate()` разбирает
   `d2i_X509`, а при неудаче — `d2i_PKCS7`, извлекает сертификат(ы) из
   `p7->d.sign->cert`; при нескольких сертификатах берёт первый в стеке
   (осознанное упрощение — выбор "по subject ожидаемого issuer" не
   реализован, т.к. `FetchIntermediateCertRequest` эту информацию не
   передаёт). См. README.md раздел «Доработки по ROADMAP.md», тесты
   `test_intermediate_cert_accepts_pkcs7_single_cert`/
   `test_intermediate_cert_accepts_pkcs7_multi_cert_takes_first` в
   `tests/test_client_server_roundtrip.cpp`.

7. **[СДЕЛАНО] [P2] Поддержка `https://` в HTTP-клиенте (опционально,
   конфигурируемо).** Было: сознательно не реализовано (см. README) —
   редкий, но не запрещённый RFC случай AIA/OCSP/CDP URL; требовал бы
   отдельного TLS-стека внутри демона (риск — тот же класс поверхности
   атаки, от которого мы изолируемся, обрабатывая недоверенные внешние
   данные). Реализовано: `SimpleHttpFetcher` умеет `https://`, но
   ВЫКЛЮЧЕНО по умолчанию — флаг `--allow-https` (плюс
   `--https-ca-bundle` для явного доверенного набора вместо системного).
   Полная проверка сертификата сервера (`SSL_VERIFY_PEER`, TLS 1.2+) и
   имени/адреса хоста (`X509_VERIFY_PARAM_set1_ip_asc` для IP-литералов,
   `set1_host` для доменных имён) — без деградации до
   неверифицированного TLS даже при ошибках конфигурации. См. README.md
   раздел «Доработки по ROADMAP.md», отдельный тестовый бинарник
   `tests/test_https_support.cpp` с настоящим TLS-сервером на 127.0.0.1
   (не заглушкой).

8. **[СДЕЛАНО] [P2] Delta CRL (RFC 5280 §5.2.4).** Было: некоторые CA
   публикуют delta-CRL (список изменений с момента последнего полного
   CRL) через отдельный URL в расширении `freshestCRL`; не разбиралось и
   не докачивалось. Реализовано — с ключевым уточнением по ходу работы:
   отдельный `FetchDeltaCrl`-путь НЕ понадобился, т.к. докачка delta-CRL
   по HTTP технически неотличима от докачки обычного CRL (существующий
   `handle_crl()`/`FetchCrlRequest` уже справляются без изменений).
   Единственный реальный пробел — разбор ASN.1 (`freshestCRL` для поиска
   URL, `deltaCRLIndicator` для подтверждения "это точно delta") — закрыт
   новым `src/crl_delta.hpp` (по аналогии с `aia.hpp`, самостоятельные
   тестируемые утилиты, не встроенные в основной путь роутера). См.
   README.md раздел «Доработки по ROADMAP.md», тесты в
   `tests/test_crl_delta_extraction.cpp`.

9. **[СДЕЛАНО] [P3] `ldap://` URL для CRL distribution points.** Было:
   ряд корпоративных и государственных PKI (типичный пример — Active
   Directory Certificate Services) публикуют CRL через LDAP, а не HTTP;
   не разбиралось и не докачивалось. Реализовано (по явному запросу,
   несмотря на пометку "делать только при реальной потребности") —
   `src/ldap_client.hpp`: минимальный LDAPv3-клиент (RFC 4511) с
   собственным BER-кодеком, `ILdapFetcher`/`SimpleLdapFetcher` за тем же
   интерфейсным подходом, что `IHttpFetcher`; anonymous bind, baseObject
   search, ограниченное подмножество LDAP Filter (RFC 4515); выключено
   по умолчанию (`--allow-ldap`, та же логика, что у `--allow-https`,
   п.7). Явное ограничение: LDAP URL с пустым host (`ldap:///...`, частый
   случай для реальных AD-CDP) не поддерживается — cert-helper не
   domain-aware. Реализация вручную сверена с настоящим OpenLDAP-сервером
   (`slapd`) — побайтовое совпадение полученного значения с оригиналом.
   См. README.md раздел «Доработки по ROADMAP.md», тесты
   `tests/test_ldap_support.cpp` и router-уровневые тесты в
   `tests/test_client_server_roundtrip.cpp`.

## 2. Надёжность и производительность (P1–P2)

10. **[СДЕЛАНО] [P1] Retry с backoff для транзиентных сетевых ошибок.**
    Было: любая сетевая ошибка (включая одиночный дропнутый пакет/RST)
    сразу возвращалась как `NetworkError` без повторной попытки.
    Реализовано: `RequestRouter::retry_with_backoff()`/
    `fetch_with_retry()` — до `max_retries` (по умолчанию 2) повторов с
    экспоненциальным backoff и full jitter, только для идемпотентных
    HTTP-операций (GET для CRL/AIA; POST для OCSP идемпотентен по факту)
    и только для сбоев транспорта, не для завершённых HTTP-ответов с
    кодом ошибки. Retry-бюджет вписан внутрь `req.timeout_ms` (не
    умножает таймаут D-Bus-вызова клиента). `ldap://`-путь (пункт 9) не
    ретраится — явная граница, не забытый край. Флаги
    `--max-retries`/`--retry-base-delay-ms`. См. README.md раздел
    «Доработки по ROADMAP.md», тесты в
    `tests/test_client_server_roundtrip.cpp`.

11. **[СДЕЛАНО] [P1] Circuit breaker per-host для проблемных
    responder'ов.** Было: если конкретный OCSP-responder/CDP регулярно
    недоступен или отвечает ошибками — демон продолжал бить в него на
    каждый handshake, увеличивая задержку для пользователей. Реализовано:
    классический Closed/Open/Half-Open паттерн в `RequestRouter`,
    ключуется по `host:port`; после `circuit_breaker_failure_threshold`
    (по умолчанию 5) подряд неудачных запросов открывается на
    `circuit_breaker_cooldown_seconds` (по умолчанию 30) — все запросы к
    хосту в это время сразу `NetworkError` без попытки соединения; далее
    Half-Open пробует восстановление. Осознанные упрощения (не забытые
    края): Half-Open пропускает все конкурентные запросы, а не строго
    один; карта breaker'ов ограничена по размеру без строгого LRU
    (защита от роста памяти, т.к. ключ частично под контролем
    недобросовестного сервера через AIA/CDP URL). `ldap://` не покрыт —
    та же граница, что и у retry (пункт 10). Флаги
    `--circuit-breaker-failure-threshold`/`--circuit-breaker-cooldown-
    seconds`/`--circuit-breaker-max-tracked-hosts`. См. README.md раздел
    «Доработки по ROADMAP.md», тесты в
    `tests/test_client_server_roundtrip.cpp`.

12. **[СДЕЛАНО] [P2] HTTP keep-alive / пул соединений к часто
    запрашиваемым хостам.** Было: одно TCP-соединение на запрос,
    `Connection: close` всегда. Реализовано в `SimpleHttpFetcher`
    (прозрачно для `IHttpFetcher`/`RequestRouter`): пул простаивающих
    соединений по `host:port`, framing ответа теперь по
    `Content-Length`/инкрементальному chunked-разбору вместо чтения до
    EOF (необходимая предпосылка для keep-alive); прозрачное (без
    backoff) восстановление после протухшего пулированного соединения —
    отдельный механизм от `retry_with_backoff()` пункта 10. Лимиты пула
    — фиксированные константы (не CLI-флаги, внутренний параметр
    производительности). См. README.md раздел «Доработки по
    ROADMAP.md», отдельный тестовый бинарник
    `tests/test_http_keepalive.cpp` с настоящим персистентным TCP-сервером.

13. **[СДЕЛАНО] [P2] DNS-кэш для имён из AIA/OCSP/CDP URL.** Было:
    каждый запрос заново резолвил DNS. Реализовано: `src/dns_cache.hpp`
    — `DnsCache`, общий для `SimpleHttpFetcher`/`SimpleLdapFetcher` (по
    экземпляру на каждый), с фиксированным коротким TTL (по умолчанию
    60с, флаг `--dns-cache-ttl-seconds`) — `getaddrinfo()` не отдаёт
    реальный TTL DNS-записи, полноценный разбор wire-формата DNS был бы
    отдельным проектом масштаба LDAP-клиента (пункт 9), поэтому выбран
    второй из двух вариантов, явно допущенных формулировкой пункта.
    Политика (`NetworkPolicy::is_address_allowed()`) по-прежнему
    проверяется для каждого адреса при каждом использовании
    закэшированной записи, не только при первом резолве — кэш DNS не
    даёт способа обойти политику. Заодно устранено дублирование
    `connect_with_timeout()` между `http_client.hpp` и `ldap_client.hpp`
    — общие `ResolvedAddress`/`make_sockaddr()` вынесены в
    `dns_cache.hpp`. См. README.md раздел «Доработки по ROADMAP.md»,
    тесты в `tests/test_dns_cache.cpp` (внедряемый резолвер) и
    `test_dns_cache_does_not_bypass_policy_on_repeated_use` в
    `tests/test_http_cache_hints.cpp`.

14. **[СДЕЛАНО] [P2] Батчинг OCSP-запросов (RFC 6960 допускает несколько
    `Request` в одном `OCSPRequest`).** Было: tls-mitm делал отдельный
    D-Bus-вызов и HTTP round-trip на каждый сертификат цепочки, даже
    если все они проверяются у одного responder'а. Реализовано: новый
    D-Bus метод `FetchOcspBatch(a(sayu)) -> a(yayb)` и клиентский
    `DbusClient::fetch_ocsp_batch()`; `RequestRouter::handle_ocsp_batch()`
    группирует промахи кэша по `responder_url`, строит один
    комбинированный `OCSP_REQUEST` через `OCSP_request_add0_id()`, делает
    один HTTP POST через ту же инфраструктуру retry/circuit breaker, что
    и одиночные запросы, кэширует результат под собственным ключом
    каждого исходного запроса с индивидуальным TTL по его `CertID`
    (`OCSP_resp_find()`). Несколько результатов одной группы получают
    побайтово идентичный `payload_der` (общий подписанный блок — нельзя
    разрезать подпись `tbsResponseData` на части) — задокументировано в
    `protocol.hpp` как осознанное архитектурное решение. См. README.md
    раздел «Доработки по ROADMAP.md», тесты в
    `tests/test_client_server_roundtrip.cpp` (фикстуры сгенерированы
    через OpenSSL C API — Python `cryptography` не поддерживает несколько
    `SingleResponse` в одном ответе, см. `test_certs/README.md`).

15. **[СДЕЛАНО] [P3] Прогрев кэша (cache warm-up) при старте.** Было:
    первые запросы сразу после рестарта/деплоя всегда были "холодными".
    Реализовано: флаг `--warmup-file <путь>`, `src/cache_warmup.hpp` —
    построчный файл с записями `crl:<url>`/`aia:<url>`/
    `ocsp:<responder_url>:<cert_path>:<issuer_path>` (для `ocsp:` нужны
    оба файла сертификата — `CertID` строится из subject+issuer через
    `OCSP_cert_to_id()`, URL одного responder'а сам по себе не говорит,
    статус какого сертификата прогревать). Выполняется в фоновом потоке
    сразу после старта D-Bus сервера — не блокирует готовность демона.
    См. README.md раздел «Доработки по ROADMAP.md», тесты в
    `tests/test_cache_warmup.cpp`.

16. **[СДЕЛАНО] [P3] Экспорт/импорт кэша между хостами.** Было: для
    миграции/клонирования инсталляции каждый узел приходилось
    "прогревать" с нуля. Реализовано: отдельный CLI-бинарник
    `cert-helper-cache-tool export|import` (не D-Bus клиент — работает
    напрямую с каталогом кэша, не требует запущенного демона) и
    `src/cache_export.hpp` — собственный простой портируемый формат
    поверх уже хостонезависимого on-disk формата `FileCacheStore` (имя
    файла — `sha256(kind|key)`, содержимое без host-specific полей: в
    принципе сработал бы и голый `cp -r`/`rsync`, но экспорт/импорт даёт
    один переносимый файл, отсеивает просроченные записи и сводку).
    Работает НИЖЕ уровня `ICacheStore` — сознательно, не расширяя
    интерфейс ради узкого сценария CLI-утилиты. Проверка на просрочку —
    и на экспорте, и на импорте (запись могла протухнуть за время
    переноса файла между хостами). См. README.md раздел «Доработки по
    ROADMAP.md», тесты в `tests/test_cache_export.cpp`.

17. **[P3] Разделяемый (shared) бэкенд кэша для кластера демонов.**
    Раздел 1.1 исходного ТЗ упоминал сценарий нескольких NGFW-воркеров;
    если демон тоже станет многоинстансным (не один процесс на хост, а
    несколько за балансировщиком) — понадобится общий кэш поверх
    Redis/Memcached/etc. как альтернативная реализация `ICacheStore`,
    без изменений в `RequestRouter`.

18. **[P2] Явное версионирование D-Bus интерфейса.** Сейчас интерфейс

## 4. Наблюдаемость и эксплуатация (P1–P2)

21. **[P1] Экспорт метрик в формате Prometheus/OpenMetrics.** Сейчас
    метрики доступны только через D-Bus `HealthCheck` (нужен явный
    вызов). Полезно поднять локальный HTTP-эндпоинт `/metrics` (или
    отдельный unix-сокет) с теми же данными в текстовом
    Prometheus-формате — стандартная практика для инфраструктурных
    демонов (аналог `/metrics` у Envoy, HAProxy stats page, node_exporter).

22. **[P1] Структурированное логирование вместо `fprintf(stderr, ...)`.**
    Перейти на JSON-логи (или как минимум единообразный
    `[timestamp] [level] [component] message`) с уровнями
    (`debug`/`info`/`warn`/`error`) — упрощает разбор в
    ELK/Loki/journald-структурированных полях (`sd_journal_send` из того
    же `libsystemd`, который уже используется под sd-bus).

23. **[P1] Аудит-лог решений о фетче.** Для регуляторных сред (NGFW часто
    используется в контурах с требованиями аудита) — отдельный
    append-only лог "что докачивали, откуда, с каким результатом,
    когда" — не то же самое, что метрики (агрегаты), а именно
    построчный журнал событий.

24. **[P1] Более детальная разбивка ошибок в `HealthCheck`.** Сейчас
    `errors` — агрегат `Timeout + NetworkError + InvalidResponse`.
    Разбивка по подтипу (сколько именно таймаутов, сколько сетевых
    ошибок, сколько "сервер ответил, но не разобрать") — упростит
    диагностику ("это CA недоступен" vs "CA отвечает не тем, что мы
    ожидаем").

25. **[P2] Конфигурационный файл (YAML/TOML/JSON) в дополнение к CLI-флагам.**
    Текущий набор флагов (`--min-worker-threads`, `--allow-cidr` и т.д.)
    уже довольно большой; конфиг-файл упростит управление в
    инфраструктуре как код (Ansible/Puppet/etc.), где генерировать один
    файл проще, чем длинную командную строку. `boost::program_options`
    уже поддерживает чтение из файла теми же `options_description` —
    относительно небольшая доработка `daemon_main.cpp`.

26. **[P2] Горячая перезагрузка конфигурации по SIGHUP.** Для правок
    сетевой политики/лимитов кэша без полного рестарта (и, значит, без
    сброса in-memory кэша) — типичный паттерн для долгоживущих демонов
    (nginx, tor, unbound).

27. **[P2] `--check-config` / dry-run режим.** Проверить, что конфигурация
    (флаги или файл) валидна, без реального старта D-Bus сервиса —
    полезно для CI/pre-deploy валидации.

28. **[P2] `--version`.** Простая, но обычно ожидаемая опция — версия
    сборки, git-хэш, версия используемого протокола D-Bus.

29. **[P3] Web-панель/CLI-дашборд для живого просмотра метрик.**
    Не приоритет для демона такого профиля, но упоминается как "видели у
    других" (Squid имеет `cachemgr.cgi`) — возможный будущий инструмент
    поверх уже существующего `HealthCheck`/`/metrics`.

## 5. Тестирование и качество (P1–P2)

30. **[P1] Fuzzing для парсеров недоверенных данных.** `aia.hpp`
    (X.509/ASN.1 через OpenSSL), `http_client.hpp` (разбор HTTP-ответа,
    chunked decoding, Cache-Control/Expires) — весь код, трогающий байты
    от внешнего сервера, обрабатывает потенциально враждебный ввод и
    выигрывает от libFuzzer/AFL-гарнесса, встроенного в CI.

31. **[P1] Сборка и прогон тестов под ASan/UBSan/TSan.** Демон
    многопоточный (эластичный пул воркеров, D-Bus bus-поток,
    thread-safe кэш) — санитайзеры особенно ценны для гонок и
    use-after-free, которые юнит-тесты не гарантированно ловят.

32. **[P2] CI-пайплайн (GitHub Actions/GitLab CI).** Автоматический
    прогон `ctest` + fuzzing (короткие сессии) + санитайзеров на каждый
    PR — сейчас сборка и тесты запускаются только вручную.

33. **[P2] Property-based / генеративные тесты для `NetworkPolicy`.**
    Текущие юнит-тесты — набор конкретных примеров CIDR. Генеративное
    тестирование (случайные IP + случайные CIDR-правила, сверка с
    независимой референсной реализацией через Python `ipaddress`) даст
    более высокую уверенность в отсутствии edge-case багов в разборе
    префиксов.

34. **[P2] Нагрузочное тестирование / бенчмарк пула воркеров.**
    Проверить поведение эластичного пула (пункт 4 из анализа Squid) под
    реальной нагрузкой — сколько воркеров реально поднимается при
    N параллельных медленных запросов, насколько быстро схлопывается
    простаивающий пул, нет ли деградации при `max_worker_threads`,
    достигнутом одновременно с большой очередью.

35. **[P3] End-to-end тест с реальными публичными CA (в CI, ограниченно).**
    Текущие тесты сознательно не ходят в интернет. Отдельный,
    промаркированный как "требует сети" набор тестов против реальных
    публичных OCSP-responder'ов/CRL (например, Let's Encrypt) — полезен
    для регрессии на реальных форматах ответов, но должен быть явно
    опциональным (не в стандартном `ctest`, чтобы не ломать CI при
    сетевых проблемах или rate-limit).

## 6. Развёртывание и упаковка (P2–P3)

36. **[P2] `.deb`/`.rpm` пакеты.** Сейчас — только сборка из исходников +
    вручную разложенные systemd unit/D-Bus policy. Нативные пакеты для
    Debian/Ubuntu и RHEL/CentOS с правильными
    `postinst`/`postrm`-скриптами (создание пользователя/группы,
    директорий с нужными правами) упростят эксплуатацию.

37. **[P2] Docker-образ (для тестовых/staging окружений).** Не для прода
    NGFW (там демон обычно нативный процесс рядом с самим NGFW), но
    полезен для быстрого локального тестирования интеграции
    tls-mitm ↔ cert-helper без разворачивания полного хоста.

38. **[P3] Ansible-роль / Terraform-модуль для типового развёртывания.**
    Обёртка над systemd unit + D-Bus policy + созданием пользователя —
    снижает трение при первом внедрении в новую инфраструктуру.

39. **[P3] Формальная модель угроз (threat model) документом.**
    Частично уже присутствует неявно в комментариях (SSRF-защита,
    изоляция парсинга недоверенных данных) — свести в отдельный
    структурированный документ (STRIDE или аналог) для security review
    перед продовым использованием.

## 7. Часть 2 исходного ТЗ (интеграция в tls-mitm)

40. **[P1, отдельный трек] Реализация раздела 7 исходного ТЗ.** Сама
    доработка `tls-mitm` для реального использования AIA-докачки в
    процессе построения цепочки доверия — рекомендованный подход:
    re-verify после handshake на отдельном `X509_STORE_CTX`, а не
    вмешательство в `verify_callback` (см. README и исходное ТЗ, раздел
    7 п.3). Требует исходников `tls-mitm-project`, которых не было в
    предыдущих сессиях. Отдельный набор тестов по аналогии с
    `tests/test_revocation.cpp`.

41. **[P2] Проактивный вызов AIA/revocation фетчеров, а не только как
    fallback при ошибке.** По итогам анализа `ssl_crt_validator`
    (Squid консультирует внешний валидатор "независимо от результата"
    встроенной проверки) — рекомендация для интеграции: не полагаться
    только на `X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT_LOCALLY` как триггер,
    рассмотреть более широкий набор условий.

## Как читать этот список дальше

Каждый пункт самодостаточен и может быть взят в отдельную задачу/сессию
без контекста остальных — так и планировался этот документ, учитывая
ограничения по объёму одной рабочей сессии. Раздел 1 (безопасность и
корректность TTL/кэша) реализован целиком, пункты 1–9; из раздела 2
реализованы пункты 10–16 (retry с backoff, circuit breaker, HTTP
keep-alive, DNS-кэш, батчинг OCSP, прогрев кэша, экспорт/импорт кэша) —
см. пометки **[СДЕЛАНО]** выше и README.md, раздел «Доработки по
ROADMAP.md». Рекомендуемый порядок при следующей итерации: P1 из
раздела 4 (наблюдаемость — Prometheus/структурные логи, важны для
production-эксплуатации) и/или п.17 раздела 2 (shared backend для
кластера — существенно более редкий сценарий, требует выбора и
интеграции внешнего хранилища, не делать без реальной потребности),
остальное — по мере появления реальной потребности (YAGNI, тот же
принцип, что применялся во всех предыдущих решениях по этому проекту).
